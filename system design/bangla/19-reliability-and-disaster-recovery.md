# অধ্যায় ১৯ — Reliability ও Disaster Recovery 🟡

> ব্যর্থতা ঠেকিয়ে নির্ভরযোগ্যতা অর্জিত হয় না। ব্যর্থতা নিশ্চিত।
> নির্ভরযোগ্যতা অর্জিত হয় **ব্যর্থতাকে টিকে থাকার যোগ্য, সীমাবদ্ধ আর একঘেয়ে করে**।
>
> দুটো সংখ্যা এই পুরো অধ্যায় চালায়: **RTO** (আমরা কত দ্রুত ফিরতে পারি?) আর **RPO** (আমরা কতটা data হারাতে পারি?)। প্রতিটা সিস্টেমের জন্য দুটোই ঝাড়া মুখস্থ জানুন।

## ১৯.১ পরিভাষা, নিখুঁতভাবে

মানুষ এই শব্দগুলো ঢিলেঢালাভাবে ব্যবহার করে আর তারপর ভুল জিনিস বানায়। নিখুঁত হোন।

| শব্দ | মানে | উদাহরণ |
|------|---------|---------|
| **Availability** | এটা কি *এই মুহূর্তে* চালু? | ৯৯.৯% সময় request সফল হয় |
| **Reliability** | এটা কি *সময়ের সাথে সঠিকভাবে* কাজ করে? | ৩ বছরে এটা data নষ্ট করেনি |
| **Durability** | Data কি টিকে থাকবে? | S3-র ১১টা নাইন — প্রতি ১ কোটি বছরে প্রতি ১০,০০০ object-এ একটা হারায় |
| **Fault tolerance** | একটা ব্যর্থতা *সত্ত্বেও* কাজ করে | একটা node মরে; কোনো ব্যবহারকারী টের পান না |
| **High availability (HA)** | স্বয়ংক্রিয় পুনরুদ্ধার, ন্যূনতম downtime | ৬০ সেকেন্ডে failover |
| **Disaster recovery (DR)** | একটা *বড় মাপের* ঘটনা থেকে পুনরুদ্ধার | একটা পুরো region নেই; অন্য জায়গায় ফেরান |
| **Resilience** | ধাক্কা শুষে নেয় আর মানিয়ে নেয় | Load-এ ধাপে ধাপে দুর্বল হয় |

**HA বনাম DR — এই পার্থক্যটাই মানুষ সবচেয়ে বেশি ঘুলিয়ে ফেলে:**

```
HIGH AVAILABILITY            DISASTER RECOVERY
পরিসর:    একটা component      পরিসর:    পুরো সিস্টেম/সাইট
কারণ:     node/AZ-র ব্যর্থতা    কারণ:     region হারানো, ransomware, data নষ্ট
সাড়া:     স্বয়ংক্রিয়            সাড়া:     সাধারণত একটা মানবিক সিদ্ধান্ত
সময়:      সেকেন্ড–মিনিট        সময়:      মিনিট–দিন
খরচ:      মাঝারি               খরচ:      উল্লেখযোগ্য
```

> **HA আপনাকে DR দেয় না।** Multi-AZ database replication আপনাকে একটা datacenter-এর ব্যর্থতা থেকে রক্ষা করে। কেউ `DELETE FROM orders` চালালে এটা আপনাকে রক্ষা করে **না** — ওই statement মিলিসেকেন্ডে প্রতিটা replica-তে নিখুঁতভাবে replicate হয়। **শুধু backup-ই আপনাকে যৌক্তিক বিকৃতি থেকে রক্ষা করে।** এই বিভ্রান্তি কোম্পানি শেষ করে দিয়েছে।

## ১৯.২ RTO আর RPO ⭐ 🟢

```
        ◄────── RPO ──────►│◄────── RTO ──────►
   ─────┬──────────────────┬───────────────────┬──────►  সময়
        │                  │                   │
   শেষ ভালো             বিপর্যয়             service
   backup/replica                          ফিরে এলো

   RPO = আপনি কতটা DATA হারানোর সামর্থ্য রাখেন  (ব্যর্থতা থেকে পেছনে মাপা)
   RTO = আপনি কতক্ষণ বন্ধ থাকার সামর্থ্য রাখেন   (সামনে মাপা)
```

### Business থেকে আসল সংখ্যা কীভাবে পাবেন

*"আপনার কোন RPO লাগবে?"* জিজ্ঞেস করবেন না — সবাই শূন্য বলে। ফলাফল নিয়ে জিজ্ঞেস করুন:

| প্রশ্ন | এটা কী প্রকাশ করে |
|----------|-----------------|
| "শেষ এক ঘণ্টার data হারালে আপনাকে কী করতে হতো?" | RPO-র সহনশীলতা, আর data আবার বানানো যায় কিনা |
| "মঙ্গলবার সকালে ৪ ঘণ্টা বন্ধ থাকলে কী হয়?" | RTO-র সহনশীলতা |
| "শেষ এক ঘণ্টা কি ইমেইল, কাগজ, বা partner-এর সিস্টেম থেকে আবার বানাতে পারতেন?" | একটা বড় RPO সত্যিই টেকার মতো কিনা |
| "Customer-দের কী বলতেন?" | সুনামের খরচ |
| "কোনটা খারাপ: ৮ ঘণ্টা বন্ধ, নাকি ১৫ মিনিটের transaction হারানো?" | **RTO/RPO-র অগ্রাধিকার** — আর এগুলো প্রায়ই পরস্পরবিরোধী |

**একটা কোম্পানির আলাদা সিস্টেম আলাদা সংখ্যার যোগ্য:**

| সিস্টেম | RPO | RTO | যুক্তি |
|--------|-----|-----|-----------|
| Payment ledger | **০** | ১৫ মিনিট | আর্থিক আর আইনি; কিছুই হারানো যাবে না |
| Verification session | ৫ মিনিট | ১ ঘণ্টা | ব্যবহারকারী session আবার করতে পারেন |
| Audit log | ০ | ২৪ ঘণ্টা | হারানো যাবে না; পরে পড়া যায় |
| Analytics warehouse | ২৪ ঘণ্টা | ৪৮ ঘণ্টা | উৎস-সিস্টেম থেকে আবার বানানো যায় |
| Marketing সাইট | ২৪ ঘণ্টা | ৪ ঘণ্টা | কম প্রভাব |

> **সব সিস্টেমে একই RTO/RPO একটা design-এর দুর্গন্ধ।** এর মানে কেউ জিজ্ঞেসই করেনি, আর আপনি হয় অগুরুত্বপূর্ণ অংশের জন্য বেশি দিচ্ছেন নয়তো গুরুত্বপূর্ণগুলো কম রক্ষা করছেন।

**খরচের বক্ররেখা খাড়া আর অরৈখিক:**

```
RPO = ২৪ঘ    রাতের backup                                $
RPO = ১ঘ     ঘণ্টায় snapshot + WAL archiving              $$
RPO = ৫মি    অবিরাম WAL পাঠানো, async replica             $$$
RPO = ০      synchronous replication (+ latency-র খরচ)    $$$$$

RTO = ২৪ঘ    backup থেকে ফেরানো, infrastructure নতুন করে   $
RTO = ৪ঘ     IaC + স্বয়ংক্রিয় restore, পরীক্ষিত              $$
RTO = ১ঘ     উষ্ণ standby                                 $$$
RTO = ৫মি    স্বয়ংক্রিয় failover সহ গরম standby              $$$$
RTO = ০      active-active multi-region                   $$$$$$
```

Business-কে এই টেবিলটা দেখান। **"RPO শূন্য"-র খরচ "RPO পাঁচ মিনিট"-এর দশ গুণ, আর শেষ কয়েক মিনিটের দাম দেখলেই আলোচনাটা সাথে সাথে বদলে যায়।**

## ১৯.৩ Redundancy আর ব্যর্থতার স্তর 🟢

```
স্তর               ব্যর্থতা                     সুরক্ষা
────────────────────────────────────────────────────────────────────
Component          Disk মরে                    RAID, replica
Process            App crash করে               Restart, একাধিক instance
Host               Server fail করে             একাধিক host, orchestration
Rack               Rack-এর বিদ্যুৎ যায়          Rack জুড়ে ছড়ান
Availability Zone  Datacenter fail করে         MULTI-AZ  ← অপরিহার্যটা
Region             Region fail করে             Multi-region DR
Cloud প্রোভাইডার    প্রোভাইডারের outage           Multi-cloud (খুব কমই যুক্তিসঙ্গত)
যৌক্তিক            খারাপ deploy / খারাপ DELETE  BACKUP + rollback  ← replication সাহায্য করে না
```

> **ওই টেবিলের শেষ লাইনটাই সবচেয়ে গুরুত্বপূর্ণ।** Redundancy *infrastructure*-এর ব্যর্থতা থেকে রক্ষা করে। এটা *যৌক্তিক* ব্যর্থতা — একটা bug, একটা খারাপ migration, একজন দূষিত ভেতরের মানুষ, বা ransomware — থেকে শূন্য সুরক্ষা দেয়। ওগুলোর জন্য backup, point-in-time recovery আর immutability লাগে।

### N+1, N+2, 2N

| মডেল | মানে | উদাহরণ |
|-------|---------|---------|
| **N** | ঠিক যতটুকু ক্ষমতা লাগে | ৪টা server load সামলায় — যে কোনো একটা হারালে সেবা দুর্বল |
| **N+1** | একটা বাড়তি | ৫টা server; একটা হারানো টেকে |
| **N+2** | দুটো বাড়তি | রক্ষণাবেক্ষণের *সময়ে* একটা ব্যর্থতা টেকে |
| **2N** | সম্পূর্ণ দ্বিগুণ | ৮টা server; অর্ধেক হারানো টেকে |

**AZ-র যে হিসাবটা মানুষ ভুল করে:**

```
আপনার ৩টা AZ জুড়ে ৬টা server-এর ক্ষমতা লাগবে।
সরলভাবে:  প্রতি AZ-তে ২টা = মোট ৬।
           একটা AZ হারালে → ৪টা server → দরকারি ক্ষমতার মাত্র ৬৭% → দুর্বল।

সঠিকভাবে: এমন সংখ্যা যাতে একটা AZ হারালেও পূর্ণ ক্ষমতা থাকে।
           প্রতি AZ-তে ৩টা = মোট ৯। একটা AZ হারালে → ৬টা বাকি → পূর্ণ ক্ষমতা। ✅
```

**নিয়ম: N-টা availability zone থাকলে প্রতিটা AZ মোট দরকারি ক্ষমতার ১/(N−১)-এর বেশি বহন করতে পারবে না।** ৩টা AZ-তে আপনি ন্যূনতমের ১.৫× চালান। ওই ৫০% বাড়তিই একটা AZ হারিয়েও দুর্বল না হওয়ার দাম — আর সেটা incident-টার চেয়ে অনেক সস্তা।

### Active-active বনাম active-passive

| | **Active-Passive** | **Active-Active** |
|---|---|---|
| Standby | অলস (বা কিছুই পরিবেশন করছে না) | Traffic পরিবেশন করছে |
| Failover | Standby-কে পদোন্নতি | Traffic কেবল সরে যায় |
| RTO | মিনিট | সেকেন্ড |
| খরচের দক্ষতা | অর্ধেক ক্ষমতা অলস | সব ক্ষমতা ব্যবহৃত |
| জটিলতা | কম | **অনেক বেশি** — সংঘর্ষের সমাধান, data-র consistency |
| আত্মবিশ্বাস | দরকার না পড়া পর্যন্ত **standby অপরীক্ষিত** | অবিরাম প্রমাণিত |

> **Active-active-এর লুকানো যুক্তিটা: একটা অপরীক্ষিত standby সাধারণত কাজ করে না।** Configuration ভেসে যায়, certificate-এর মেয়াদ শেষ হয়, ক্ষমতা কখনো যাচাই হয়নি। Active-active অবিরাম ব্যবহৃত হয়। আপনি যদি একটা দ্বিতীয় সাইট বানানই, তাহলে সেটাকে সত্যিকারের traffic — এমনকি ১০% — বহন করানোর কথা গুরুত্বের সাথে ভাবুন, যাতে আপনি জানেন এটা কাজ করে।

## ১৯.৪ Disaster recovery-র pattern 🟢

চারটা প্রচলিত pattern, ক্রমবর্ধমান খরচ আর হ্রাসমান RTO-তে।

### ১. Backup and Restore

```
Primary region: সবকিছু চলছে
DR region:      কিছুই না — শুধু object storage-এ backup

বিপর্যয় → infrastructure বানান (IaC) → data ফেরান → DNS ঘোরান
```

| RTO | RPO | খরচ | কীসের জন্য |
|-----|-----|------|---------|
| ঘণ্টা থেকে দিন | ঘণ্টা | **$** (শুধু storage) | ভেতরের টুল, dev, কম-গুরুত্বের সিস্টেম |

**এটা তখনই সম্ভব যখন আপনার infrastructure পুরোপুরি কোডে** (অধ্যায় ১৬)। IaC ছাড়া "infrastructure বানান" মানে ঘণ্টা নয়, সপ্তাহ।

### ২. Pilot Light

```
Primary region: সবকিছু চলছে
DR region:      database replica চলছে + AMI/image প্রস্তুত; compute বন্ধ

বিপর্যয় → compute চালু করুন (আগেই বানানো image) → DB-কে পদোন্নতি → DNS ঘোরান
```

| RTO | RPO | খরচ | কীসের জন্য |
|-----|-----|------|---------|
| ১০ মিনিট – ২ ঘণ্টা | সেকেন্ড থেকে মিনিট | **$$** | বেশিরভাগ business সিস্টেম — **সাধারণত সেরা মূল্য** |

"Pilot light" হলো সবসময়-চালু data replication। Compute চালু করা সস্তা; data সরানো ধীর। ওই অসমতাই এই pattern-টাকে এত ভালো কাজ করায়।

### ৩. Warm Standby

```
Primary region: পূর্ণ ক্ষমতা
DR region:      একটা ছোট করা কিন্তু চলমান কপি (ধরুন ১০-২৫% ক্ষমতা)

বিপর্যয় → বাড়ান → traffic সরান
```

| RTO | RPO | খরচ | কীসের জন্য |
|-----|-----|------|---------|
| ৫ – ৩০ মিনিট | সেকেন্ড | **$$$** | আয়-গুরুত্বপূর্ণ সিস্টেম |

**Pilot light-এর উপর সুবিধা: এটা অবিরাম চলছে, তাই আপনি জানেন এটা কাজ করে।** একটা live test হিসেবে আপনি এমনকি অল্প শতাংশ আসল traffic এখানে পাঠাতে পারেন।

### ৪. Multi-site Active-Active

```
দুটো region-ই traffic পরিবেশন করছে, data দ্বিমুখীভাবে replicate বা region অনুযায়ী ভাগ করা
```

| RTO | RPO | খরচ | কীসের জন্য |
|-----|-----|------|---------|
| প্রায় শূন্য | প্রায় শূন্য | **$$$$$$** | বৈশ্বিক scale, বা একটা নিয়ন্ত্রক দাবি |

**কঠিন অংশটা কখনোই compute নয় — এটা data।** দ্বিমুখী replication মানে write-এর সংঘর্ষ (অধ্যায় ০৪ §৪.৮)। প্রচলিত সমাধান: region অনুযায়ী ভাগ করুন (EU-র ব্যবহারকারীরা শুধু EU-তে লেখেন), একটা বৈশ্বিকভাবে consistent database ব্যবহার করুন (Spanner/CockroachDB, latency-র দাম দিয়ে), বা এমন data type design করুন যা মিশে যায় (CRDT)।

### বেছে নেওয়া

```
N ঘণ্টা downtime-এর business খরচ কত?
├── তুচ্ছ           → Backup & Restore
├── অর্থপূর্ণ         → Pilot Light          ← বেশিরভাগ সিস্টেম এখানেই পড়ে
├── তীব্র            → Warm Standby
└── বিপর্যয়কর, বা নিয়ন্ত্রক-বাধ্যতামূলক → Active-Active
```

> **Active-active-এ লাফ দেওয়া নিয়ে সন্দিহান থাকুন।** এটা স্থায়ীভাবে আপনার খরচ আর জটিলতা বহুগুণ করে। বেশিরভাগ ব্যবসা একটা বিরল ২ ঘণ্টার regional outage-এ যত সহজে টেকে, একটা বৈশ্বিকভাবে consistent architecture-এর চলমান engineering-টানে তত সহজে টেকে না।

## ১৯.৫ Backup 🟢

### 3-2-1 নিয়ম (আর এর আধুনিক সম্প্রসারণ)

```
৩ কপি data
২ ভিন্ন মাধ্যম/storage-এর ধরন
১ কপি অন্য জায়গায় (ভিন্ন region বা প্রোভাইডার)
──────────────────────────────────────────────
+১ কপি IMMUTABLE / air-gapped     ← ransomware-এর উত্তর
+০ ত্রুটি, testing দিয়ে যাচাই করা    ← যে অংশটা সবাই এড়িয়ে যায়
```

**Immutability এখন কেন গুরুত্বপূর্ণ:** আধুনিক ransomware বিশেষভাবে backup খুঁজে আগে সেগুলোই encrypt করে। Object Lock / WORM storage মানে পূর্ণ admin credential সহ একজন আক্রমণকারীও retention-এর সময়সীমার মধ্যে backup মুছতে বা বদলাতে **পারবে না**। এটা আজ উপলব্ধ সবচেয়ে বেশি-মূল্যের, সবচেয়ে কম-পরিশ্রমের নিয়ন্ত্রণগুলোর একটা।

### Backup-এর ধরন

| ধরন | কী জমা রাখে | Restore | Trade-off |
|------|---------------|---------|-----------|
| **Full** | সবকিছু | দ্রুত, এক ধাপ | বড়, নিতে ধীর |
| **Incremental** | যে কোনো ধরনের শেষ backup-এর পর থেকে পরিবর্তন | ধীর — full + **প্রতিটা** increment লাগে | ছোট; একটা increment হারালে শৃঙ্খল ভাঙে |
| **Differential** | শেষ **full**-এর পর থেকে পরিবর্তন | Full + একটা differential | মাঝামাঝি |
| **Continuous / PITR** ⭐ | Base + transaction log | **যে কোনো সময়ে** | সেরা RPO; বেশি জটিল |

Database-এর জন্য **point-in-time recovery-ই গুরুত্বপূর্ণটা** (অধ্যায় ০৯)। "১৪:২০-র খারাপ migration-এর ঠিক আগে, ১৪:১৯-এ ফেরান" — একটা আসল incident-এ আপনার ঠিক এই ক্ষমতাটাই চাই।

### যে নিয়মগুলো আসলে গুরুত্বপূর্ণ

```
১. AUTOMATE      একটা manual backup এমন একটা backup যা তৃতীয় মাসে বন্ধ হয়ে যায়
২. VERIFY        Backup শেষ হয়েছে আর পড়া যায় — দুটোই যাচাই করুন; একটা ০-byte ফাইলও "সফল" হয়
৩. RESTORE TEST  ⭐ ত্রৈমাসিক, সময় মেপে, নথিভুক্ত। এটাই একমাত্র আসল প্রমাণ।
৪. অন্য জায়গায়    অন্তত ভিন্ন region; গুরুত্বপূর্ণ data-র জন্য ভিন্ন প্রোভাইডার বা account
৫. IMMUTABLE     Object Lock, যাতে ransomware এটা ধ্বংস করতে না পারে
৬. ENCRYPT       বিশ্রামে আর পথে; key backup থেকে আলাদা জায়গায়
৭. RETAIN        নীতি অনুযায়ী: দৈনিক ৩০দিন, সাপ্তাহিক ১২সপ্তাহ, মাসিক ১২মাস, বার্ষিক ৭বছর
৮. DOCUMENT      এমন একটা restore runbook যা এটা না-বানানো কেউ অনুসরণ করতে পারেন
৯. MONITOR       Backup ব্যর্থতায় আর backup-এর বয়সে alert দিন
১০. আলাদা ACCESS  Backup মুছতে production-এর চেয়ে আলাদা credential লাগা উচিত
```

> **যে লাইনটা মনে রাখবেন: "যে backup আপনি কখনো restore করেননি সেটা backup নয় — সেটা একটা আশা।"**
>
> প্রথম restore মহড়ায় সাধারণ আবিষ্কার: নথিভুক্ত ১ ঘণ্টার restore-এ আসলে ৯ ঘণ্টা লাগে, runbook-এ এমন একজনের নাম যিনি চলে গেছেন, আর কারও কাছে decryption key নেই। **একটা আসল outage-এর সময় নয়, একটা মঙ্গলবার বিকেলে এটা শেখা অনেক ভালো।**

### Restore-এর মহড়া

```
১. এটা নির্ধারণ করুন। ত্রৈমাসিক। ক্যালেন্ডারে একটা আসল প্রতিশ্রুতি হিসেবে রাখুন।
২. একটা এলোমেলো সাম্প্রতিক backup বাছুন — বিশেষভাবে প্রস্তুত করা একটা নয়।
৩. একটা বিচ্ছিন্ন পরিবেশে restore করুন।
৪. সময় মাপুন। তাত্ত্বিক নয়, আসল RTO লিপিবদ্ধ করুন।
৫. Data যাচাই করুন: row-সংখ্যা, checksum, একটা business-স্তরের যুক্তি-যাচাই।
৬. যিনি runbook লেখেননি এমন কাউকে দিয়ে করান।
৭. যা যা ভুল হলো সব লিখে রাখুন। Runbook ঠিক করুন। Automation ঠিক করুন।
```

৬ নম্বর ধাপটাই আসল ফাঁকগুলো খুঁজে বের করে।

## ১৯.৬ ব্যর্থতা শনাক্তকরণ আর failover 🟢

### Health check

```
অগভীর:  "Process কি সাড়া দিচ্ছে?"           → দ্রুত, সস্তা, কম মিথ্যা-নেতিবাচক
গভীর:   "এটা কি DB, cache আর ভেন্ডরে পৌঁছাতে পারে?" → আসল সমস্যা ধরে,
                                                     তবে cascading ব্যর্থতার ঝুঁকি
```

(অধ্যায় ১৫ §১৫.৭ probe-বিপর্যয়গুলো ঢাকে। একই শিক্ষা এখানেও খাটে: যে health check একটা ভাগ করা dependency-র উপর নির্ভর করে সেটা পুরো fleet-কে একসাথে অসুস্থ চিহ্নিত করবে।)

**Synthetic monitoring** হলো বাইরে-থেকে-ভেতরে পরিপূরক: আপনার infrastructure-এর বাইরে থেকে প্রতি মিনিটে চালানো একটা script করা ব্যবহারকারী-যাত্রা। এটা এমন জিনিস ধরে যা ভেতরের health check পারে না — একটা DNS ব্যর্থতা, একটা মেয়াদোত্তীর্ণ certificate, একটা ভাঙা CDN configuration, বা একটা পুরো-region-এর সমস্যা। প্রতিটা গুরুত্বপূর্ণ যাত্রার একটা করে থাকা উচিত।

### Failover-এর কলকব্জা

```
১. DETECT     N বার ধারাবাহিকভাবে health check fail করে
২. DECIDE     এটা কি আসল, নাকি একটা নেটওয়ার্ক ঝাঁকুনি? (quorum, অধ্যায় ০৫)
৩. PROMOTE    একটা standby primary হয় (আগে পুরনোটা fence করুন!)
৪. REDIRECT   DNS / load balancer / connection string
৫. VERIFY     নতুন primary কি সত্যিই ঠিকভাবে পরিবেশন করছে?
```

**Failover-এর বিপদ — প্রতিটাই সত্যিকারের সিস্টেম কামড়েছে:**

| বিপদ | ফলাফল | উপশম |
|--------|-------------|-----------|
| **Split brain** | দুটো primary write নেয়; data অপূরণীয়ভাবে দ্বিধাবিভক্ত | Quorum, fencing token, STONITH (অধ্যায় ০৫) |
| **Flapping** | একটা মাঝে-মাঝে হওয়া ত্রুটিতে বারবার failover/failback | Hysteresis; N বার ধারাবাহিক ব্যর্থতা দাবি করুন; cooldown |
| **ঠান্ডা standby** | Standby load সামলাতে পারে না বা ভেসে গেছে | উষ্ণ রাখুন; test করুন; ক্ষমতা যাচাই করুন |
| **DNS caching** | Client মৃত primary ব্যবহার করতেই থাকে | আগেভাগে প্রস্তুত করা কম TTL; Anycast/load-balancer failover-কে প্রাধান্য দিন |
| **Failback-এর চমক** | Primary এখনো অস্থির থাকতেই স্বয়ংক্রিয় failback | **Failback manual আর ইচ্ছাকৃত করুন** |
| **পদোন্নতিতে data হারানো** | Async replica পিছিয়ে ছিল; replicate না হওয়া write শেষ | আপনার replication lag জানুন; নীতিটা incident-এর *আগেই* ঠিক করুন |

> **যে সিদ্ধান্তটা আপনাকে আগেভাগে নিতে হবে, রাত ৩টায় নয়:** আপনার async replica যদি ৪০ সেকেন্ড পিছিয়ে থাকে, আপনি কি সেটাকে পদোন্নতি দেবেন (৪০ সেকেন্ডের data হারিয়ে) নাকি primary ফেরার অপেক্ষা করবেন (downtime বাড়িয়ে)? **এটা একটা RPO/RTO trade-off আর এটা একটা business সিদ্ধান্ত।** Runbook-এ লিখে রাখুন।

## ১৯.৭ Chaos engineering 🟡

**ধারণা:** নিয়ন্ত্রিতভাবে ইচ্ছাকৃত ব্যর্থতা ঢোকান, যাতে দুর্বলতাগুলো আপনাকে খুঁজে পাওয়ার আগে আপনি সেগুলো খুঁজে পান।

**ভিত্তি:** আপনার সিস্টেমে এই দুর্বলতাগুলো ইতিমধ্যেই আছে। একমাত্র প্রশ্ন হলো আপনি সেগুলো একটা মঙ্গলবার বিকেলে সবাই উপস্থিত থাকতে আবিষ্কার করবেন, নাকি একটা ছুটির দিনে রাত ৩টায়।

### পদ্ধতি

```
১. STEADY STATE সংজ্ঞায়িত করুন   একটা মাপা-যায় স্বাভাবিক (যেমন মিনিটে verification, p99 latency)
২. অনুমান করুন                  "একটা AZ fail করলে throughput ৫%-এর মধ্যে থাকবে"
৩. BLAST RADIUS সীমিত করুন      staging-এ শুরু করুন; তারপর production-এর ১% traffic
৪. ব্যর্থতা ঢোকান                instance মারুন, latency যোগ করুন, packet ফেলুন, একটা disk ভরুন
৫. দেখুন                        Steady state কি টিকল? Alert কি বাজল? কেউ কি খেয়াল করলেন?
৬. যা ভাঙল ঠিক করুন             তারপর আবার করুন
```

**যে experiment গুলো চালানোর মতো, মোটামুটি ক্রম অনুযায়ী:**

| Experiment | কী প্রকাশ করে |
|------------|----------------|
| একটা এলোমেলো pod মারুন | Retry আর load balancing কি কাজ করে? |
| একটা পুরো AZ মারুন | ক্ষমতা কি সত্যিই N+১? Health check কি ঠিক আচরণ করে? |
| একটা dependency-তে ৫০০ ms latency যোগ করুন | Timeout আর circuit breaker কি ঠিকভাবে চালু হয়? |
| একটা dependency-কে error ফেরত দেওয়ান | Fallback-এর পথ কি কাজ করে? কেউ কি কখনো এটা চালিয়েছে? |
| **Cache flush করুন** | সিস্টেম কি একটা ঠান্ডা শুরু টিকতে পারে? (অধ্যায় ১১ — বেশিরভাগ পারে না) |
| একটা disk ভরুন | মারাত্মক হওয়ার আগেই কি alert দেন? |
| Staging-এ একটা certificate-এর মেয়াদ শেষ করুন | কিছু কি আসলেই এটা শনাক্ত করে? |
| Database failover করান | Application কি আবার যুক্ত হয়? আসল RTO কত? |
| একটা node-এ CPU পূর্ণ করুন | Load shedding কি কাজ করে? |

> **স্বয়ংক্রিয় chaos নয়, একটা "game day" দিয়ে শুরু করুন।** টিমকে দুই ঘণ্টার জন্য জড়ো করুন, experiment-টা ঘোষণা করুন, staging-এ চালান, আর দেখুন কী হয়। মূল্যটা যতটা আবিষ্কারে, ততটাই *টিম সিস্টেম সম্পর্কে কী শেখে* তাতে। স্বয়ংক্রিয় অবিরাম chaos (Chaos Monkey-ধাঁচের) পরিণত শেষ অবস্থা, শুরুর বিন্দু নয়।

**পূর্বশর্ত:** ভালো observability (অধ্যায় ১৮), একটা পরীক্ষিত rollback (অধ্যায় ১৬), আর ম্যানেজমেন্টের সম্মতি। Observability ছাড়া chaos experiment চালানো শুধু এমন outage তৈরি করে যা আপনি ব্যাখ্যা করতে পারেন না।

## ১৯.৮ Incident ব্যবস্থাপনা 🟢

### একটা incident-এর সময় ভূমিকা

| ভূমিকা | দায়িত্ব |
|------|---------------|
| **Incident Commander** | সমন্বয় করেন। **Debug করেন না।** সিদ্ধান্ত নেন, কাজ track করেন। |
| **Operations lead** | আসলে তদন্ত করেন আর জিনিস বদলান |
| **Communications lead** | Status page, customer, ভেতরের stakeholder হালনাগাদ করেন |
| **Scribe** | প্রতিটা পর্যবেক্ষণ, কাজ আর সিদ্ধান্তের timestamp রাখেন |

> **সবচেয়ে মূল্যবান একটা চর্চা: Incident Commander যিনি টাইপ করছেন তিনি হতে পারবেন না।** সেরা ইঞ্জিনিয়ার যখন একটা terminal-এ মাথা গুঁজে, তখন কেউ customer-এর সাথে যোগাযোগ, escalation, বা একটা সম্পূর্ণ ভিন্ন অনুমান পরীক্ষার কথা ভাবছে না। সমন্বয়কে তদন্ত থেকে আলাদা করলে নির্ভরযোগ্যভাবে incident ছোট হয়।

### ধারা

```
১. DETECT       alert, বা একটা customer-এর অভিযোগ
২. TRIAGE       severity? ব্যবহারকারীর উপর প্রভাব? কাকে লাগবে?
৩. COMMUNICATE  Status page + ভেতরের channel, কয়েক মিনিটের মধ্যে। "আমরা দেখছি"-ও চলবে।
৪. MITIGATE     ⭐ আগে রক্তপাত বন্ধ করুন। মূল কারণ পরে।
৫. RESOLVE      পুনরুদ্ধার নিশ্চিত করুন, পুনরাবৃত্তির জন্য নজর রাখুন
৬. POSTMORTEM   দোষারোপহীন, ৫ কর্মদিবসের মধ্যে
```

**৪ নম্বর ধাপেই টিম সবচেয়ে বেশি সময় হারায়।** প্রবৃত্তি হলো কাজ করার আগে সমস্যাটা বোঝা। সঠিক ক্রম হলো: **আগে উপশম, তারপর বোঝা।** Rollback করুন। Feature flag ঘোরান। Failover করুন। Load shed করুন। একটা সুস্থ সিস্টেম আপনি ধীরেসুস্থে তদন্ত করতে পারেন; customer বন্ধ থাকলে শান্তভাবে তদন্ত করতে পারবেন না।

### দোষারোপহীন postmortem 🟢

**নীতি:** মানুষ incident ঘটায় না। **যে সিস্টেম একজন মানুষের একটা কাজকে একটা incident ঘটাতে দেয়, সেই সিস্টেমই incident ঘটায়।**

কেউ যদি production-এ একটা খারাপ migration চালিয়ে থাকেন, তাহলে আবিষ্কারটা "সারা অসাবধান ছিলেন" নয়। এটা: *কেন production-এর বিপরীতে সরাসরি একটা review-না-করা ধ্বংসাত্মক migration চালানো সম্ভব ছিল?* ওই প্রশ্নটা একটা সমাধান তৈরি করে। দোষারোপ নীরবতা তৈরি করে — আর পরের incident জানানোর বদলে লুকানো হয়।

**Postmortem-এর কাঠামো:**

```
১. সারাংশ           কী হয়েছিল, প্রভাব, সময়কাল, তিন বাক্যে
২. TIMELINE         Timestamp সহ: শনাক্তকরণ, কাজ, সিদ্ধান্ত, সমাধান
৩. প্রভাব            কতজন ব্যবহারকারী, কত request ব্যর্থ, আয়, খাওয়া SLO-বাজেট
৪. মূল কারণ          সাধারণত একটা নয়, কয়েকটা অবদানকারী বিষয়
৫. যা ভালো হয়েছিল    ⭐ ঐচ্ছিক নয় — যা কাজ করেছে তা জোরদার করুন
৬. যা খারাপ হয়েছিল    সৎভাবে
৭. কাজের তালিকা      প্রতিটার একজন মালিক আর একটা তারিখ সহ, অন্য যে কোনো কাজের মতোই track করা
৮. শিক্ষা            আমরা এখন কী আলাদাভাবে বুঝি
```

**যে metric গুলো সময়ের সাথে track করবেন:**
- **MTTD** (শনাক্ত করার গড় সময়) — ভালো alerting দিয়ে উন্নত হয়
- **MTTA** (স্বীকৃতির গড় সময়) — on-call প্রক্রিয়া দিয়ে উন্নত হয়
- **MTTR** (ফেরার গড় সময়) — rollback-এর ক্ষমতা আর runbook দিয়ে উন্নত হয়
- **Change failure rate** — testing আর review দিয়ে উন্নত হয় (অধ্যায় ১৬)

> **মালিক আর তারিখ ছাড়া কাজের তালিকা হয় না।** সবচেয়ে সাধারণ postmortem-ব্যর্থতা হলো বারোটা উন্নতি সহ একটা সুন্দর নথি, যার একটাও কখনো করা হয় না। তিনটা আসল কাজে সীমাবদ্ধ রাখুন আর সত্যিই শেষ করুন।

## ১৯.৯ নির্ভরযোগ্যতার জন্য design — আর্কিটেক্টের সিদ্ধান্ত

অধ্যায় ০৫-এর reliability pattern-এর সবকিছু প্রযোজ্য। Architecture-এর স্তরে যে পছন্দগুলো সবচেয়ে গুরুত্বপূর্ণ:

| সিদ্ধান্ত | নির্ভরযোগ্যতার প্রভাব |
|----------|-------------------|
| **Stateless service** | ব্যবহারকারীর উপর প্রভাব ছাড়াই যে কোনো instance মরতে পারে (অধ্যায় ০৪) |
| **যেখানে সম্ভব async** | একটা বন্ধ consumer মানে একটা queue, একটা ব্যর্থ request নয় (অধ্যায় ০৬) |
| **সীমাবদ্ধ blast radius** | Cell-ভিত্তিক বা প্রতি-tenant বিচ্ছিন্নতা: একটা tenant-এর সমস্যা একটা cell-এ প্রভাব ফেলে |
| **প্রতি feature-এ graceful degradation সংজ্ঞায়িত** | আংশিক সেবা কোনো সেবা না থাকার চেয়ে ভালো (অধ্যায় ০৫) |
| **গুরুত্বপূর্ণ পথ চিহ্নিত আর সুরক্ষিত** | মূল লেনদেন শেষ করতে ন্যূনতম কোন component-গুলো লাগে জানুন |
| **কোনো ভাগ করা single point of failure নেই** | সবকিছুর লাগে এমন একটা ভাগ করা cache/queue/database একটা সিস্টেম-জোড়া ঝুঁকি |
| **সব জায়গায় idempotency** | Retry আর replay নিরাপদ করে (অধ্যায় ০৫) |
| **সবকিছু কোড থেকে পুনরুৎপাদনযোগ্য** | আপনার DR পরিকল্পনা হলো `terraform apply` (অধ্যায় ১৬) |

### গুরুত্বপূর্ণ পথটা স্পষ্টভাবে চিহ্নিত করুন

```
Liveness SaaS-এর জন্য ন্যূনতম কার্যকর লেনদেন:
  API request পায় → job queue-তে → worker process করে → ফলাফল জমা → response

গুরুত্বপূর্ণ পথে থাকা component:  API, queue, worker, database, object storage
গুরুত্বপূর্ণ পথে নয়:              analytics, webhook, ইমেইল, admin console,
                                reporting warehouse

→ গুরুত্বপূর্ণ পথ multi-AZ, কড়া SLO, বেশি ক্ষমতার জায়গা,
  আর সবচেয়ে বেশি মনোযোগ পায়।
→ বাকি সবকিছু একটা verification না আটকে দুর্বল হতে বা queue-তে যেতে পারে।
```

> **এটা লিখে রাখা একজন আর্কিটেক্টের কাটানো সবচেয়ে মূল্যবান আধা ঘণ্টাগুলোর একটা।** এটা আপনাকে বলে নির্ভরযোগ্যতার বাজেট কোথায় খরচ করতে হবে, আর on-call ইঞ্জিনিয়ারকে বলে একটা incident-এ কী নিরাপদে ত্যাগ করা যায়।

### Cell-ভিত্তিক architecture ⚪🟡

সব tenant-কে সেবা দেওয়া একটা বড় সিস্টেমের বদলে কয়েকটা সম্পূর্ণ, স্বাধীন "cell" চালান, প্রতিটা একটা উপসেটকে সেবা দেয়।

```
Cell 1 → tenant A–F     (পূর্ণ stack: API, DB, cache, worker)
Cell 2 → tenant G–M     (পূর্ণ stack)
Cell 3 → tenant N–Z     (পূর্ণ stack)
```

**সুবিধা: প্রায় যে কোনো ব্যর্থতার blast radius একটা cell।** একটা খারাপ deploy, একটা poison message, একটা নিয়ন্ত্রণহীন query বা একটা গরম tenant এক-তৃতীয়াংশ customer-কে প্রভাবিত করে, সবাইকে নয়। এটা আপনাকে একটা স্বাভাবিক canary-ও দেয়: আগে একটা cell-এ deploy করুন।

খরচ হলো operational বহুগুণতা আর routing-এর জটিলতা। AWS আর অন্য বড় প্রোভাইডাররা এভাবেই blast radius সীমিত করে, আর একটা একক-cell ব্যর্থতা বাণিজ্যিকভাবে অগ্রহণযোগ্য হলে এটা ভাবার মতো হয়ে যায়।

## ১৯.১০ সাধারণ ভুল

১. **HA-কে DR ভাবা** — replication `DELETE FROM orders` থেকে রক্ষা করে না
২. **কখনো একটা restore test না করা** — বিপর্যয়ের সময় আবিষ্কার করা যে backup ভাঙা
৩. **কোনো RTO/RPO সংখ্যা নেই** — তাই প্রতিটা নির্ভরযোগ্যতার বিনিয়োগ একটা অনুমান
৪. **সবকিছুর জন্য একই RTO/RPO** — একইসাথে বেশি দেওয়া আর কম রক্ষা করা
৫. **অপরীক্ষিত standby** — এটা ভেসে গেছে, certificate-এর মেয়াদ শেষ, আর এটা load নিতে পারে না
৬. **একটা AZ হারানো টেকে না এমন ক্ষমতা** — ৬টা লাগলে ৩টা AZ জুড়ে প্রতি AZ-তে ২টা server
৭. **Production-এর একই account বা region-এ backup** — ransomware আর account-আপস দুটোই নেয়
৮. **কোনো immutable backup কপি নেই** — আধুনিক ransomware আগে backup লক্ষ্য করে
৯. **স্বয়ংক্রিয় failback** — একটা অস্থির primary আর একটা standby-র মধ্যে ওঠানামা
১০. **গভীর health check cascading ব্যর্থতা ঘটাচ্ছে** — একটা dependency-র ঝাঁকুনি সবকিছু restart করায়
১১. **কোনো runbook নেই** — প্রতিটা incident শূন্য থেকে শুরু হয়
১২. **Incident Commander-ও debug করছেন** — কেউ সমন্বয় বা যোগাযোগ করছেন না
১৩. **দোষারোপমূলক postmortem** — মানুষ সমস্যা জানানো বন্ধ করে, আর আপনি আপনার আগাম সতর্কতা হারান
১৪. **মালিক ছাড়া কাজের তালিকা** — ছয় মাস পর একই incident আবার হয়
১৫. **উপশমের আগে তদন্ত** — আপনি বোঝাপড়া গড়ার সময় customer বন্ধ থাকেন

## ১৯.১১ আর্কিটেক্টের চেকলিস্ট

**চাহিদা**
- [ ] **প্রতি সিস্টেমে** RTO আর RPO সংজ্ঞায়িত, business-এর সাথে সম্মত, লেখা আছে
- [ ] গুরুত্বপূর্ণ পথ চিহ্নিত; অ-গুরুত্বপূর্ণ component গুলো দুর্বল-হওয়া-যোগ্য হিসেবে তালিকাভুক্ত
- [ ] Availability-র লক্ষ্য একটা error budget সহ একটা SLO হিসেবে বসানো (অধ্যায় ১৮)

**Redundancy**
- [ ] গুরুত্বপূর্ণ পথের সবকিছুতে Multi-AZ
- [ ] ক্ষমতা এমনভাবে যে একটা AZ হারালেও কোনো দুর্বলতা নেই
- [ ] গুরুত্বপূর্ণ পথে কোনো single point of failure নেই
- [ ] Downtime-এর খরচের বিপরীতে DR pattern বাছা আর যুক্তিযুক্ত

**Backup**
- [ ] স্বয়ংক্রিয়, monitor করা, আর ব্যর্থতায় **আর** বয়সে alert দেওয়া
- [ ] 3-2-1 সাথে একটা immutable কপি (Object Lock)
- [ ] একটা আলাদা account/region-এ জমা; মুছতে আলাদা credential লাগে
- [ ] Encrypted, key আলাদাভাবে জমা
- [ ] Database-এর জন্য point-in-time recovery উপলব্ধ
- [ ] **ত্রৈমাসিক restore মহড়া, সময় মেপে, যিনি runbook লেখেননি তাঁকে দিয়ে**
- [ ] মাপা RTO লক্ষ্যের সাথে তুলনা করা, আর ফাঁকটা সামলানো

**ব্যর্থতা সামলানো**
- [ ] Liveness-এ অগভীর health check, readiness-এ dependency-সচেতন
- [ ] Infrastructure-এর বাইরে থেকে গুরুত্বপূর্ণ যাত্রার synthetic monitoring
- [ ] Failover পরীক্ষিত; split-brain প্রতিরোধ যাচাই করা; failback manual
- [ ] "পিছিয়ে থাকা replica-কে পদোন্নতি নাকি অপেক্ষা?" — সিদ্ধান্তটা আগেভাগে নেওয়া আর নথিভুক্ত
- [ ] প্রতিটা অ-গুরুত্বপূর্ণ dependency-তে graceful degradation সংজ্ঞায়িত

**Operations**
- [ ] প্রতিটা alert-এর জন্য runbook, রাত ৩টার জন্য লেখা
- [ ] Incident-এর ভূমিকা সংজ্ঞায়িত; Incident Commander তদন্তকারী থেকে আলাদা
- [ ] Status page আর যোগাযোগের template দরকার হওয়ার আগেই প্রস্তুত
- [ ] ৫ দিনের মধ্যে দোষারোপহীন postmortem, মালিক আর তারিখ সহ কাজের তালিকা
- [ ] MTTD / MTTR track করা আর প্রবণতা দেখা
- [ ] গত ৬ মাসে অন্তত একটা chaos game day চালানো

## ১৯.১২ নিজেকে যাচাই

১. HA বনাম DR — পার্থক্যটা আর সেই ক্লাসিক ব্যর্থতাটা দিন যা প্রমাণ করে replication কোনো backup নয়।
২. একটা timeline-এ RTO আর RPO আঁকুন। কোনটা পেছনে মাপে?
৩. একজন business stakeholder-এর কাছ থেকে সৎ RTO/RPO সংখ্যা কীভাবে বের করবেন?
৪. একটা কোম্পানির আলাদা সিস্টেমের আলাদা RTO/RPO থাকা উচিত কেন?
৫. আপনার ৩টা AZ জুড়ে ৬টা server-এর ক্ষমতা লাগবে আর একটা AZ হারিয়েও কোনো দুর্বলতা ছাড়া টিকতে হবে। আপনি কয়টা চালাবেন, আর কেন?
৬. চারটা DR pattern-এর নাম, তাদের আনুমানিক RTO, RPO আর আপেক্ষিক খরচ সহ বলুন।
৭. Pilot Light সাধারণত সেরা মূল্য কেন? এটা কোন অসমতা কাজে লাগায়?
৮. 3-2-1 আর এর দুটো আধুনিক সংযোজন বলুন। Immutability এখন কেন গুরুত্বপূর্ণ?
৯. "যে backup আপনি কখনো restore করেননি" সেটা backup নয় কেন? একটা মহড়া সাধারণত কী প্রকাশ করে?
১০. Failover-এর সময় ছয়টা বিপদ আর প্রতিটার একটা উপশম বলুন।
১১. আপনার async replica ৪০ সেকেন্ড পিছিয়ে আর primary বন্ধ। আপনি কী করবেন, আর ওই সিদ্ধান্তটা কখন নেওয়া উচিত?
১২. Chaos engineering-এর ভিত্তি কী? চালানোর মতো পাঁচটা experiment তালিকাভুক্ত করুন।
১৩. Incident Commander কেন debug করা ব্যক্তি হতে পারবেন না?
১৪. Postmortem কেন দোষারোপহীন হতে হবে? "সারা একটা খারাপ migration চালিয়েছিলেন"-কে একটা সিস্টেমগত আবিষ্কার হিসেবে আবার লিখুন।
১৫. Cell-ভিত্তিক architecture কী আর এটা আপনাকে কী দেয়?

## ১৯.১৩ মূল কথাগুলো

- **ব্যর্থতা নিশ্চিত। প্রতিরোধ নয়, টিকে থাকার জন্য design করুন।**
- **RTO আর RPO-ই দুটো সংখ্যা** — প্রতি সিস্টেমে, business-এর সাথে, লিখিতভাবে সংজ্ঞায়িত করুন
- **HA ≠ DR।** Replication আপনার ভুল নিখুঁতভাবে ছড়ায়। শুধু backup-ই যৌক্তিক ব্যর্থতা থেকে রক্ষা করে।
- **ক্ষমতাকে একটা AZ হারিয়েও দুর্বল না হয়ে টিকতে হবে** — ৩টা AZ-তে মানে ন্যূনতমের ১.৫×
- **Pilot Light সাধারণত সেরা মূল্য**: data অবিরাম replicate হয়, compute চাহিদামতো চালু হয়
- **3-2-1 সাথে immutable সাথে যাচাই করা।** Ransomware আগে backup খোঁজে।
- **যে backup আপনি কখনো restore করেননি সেটা একটা আশা।** ত্রৈমাসিক মহড়া করুন, সময় মাপুন, অপরিচিত কাউকে দিয়ে করান।
- **একটা অপরীক্ষিত standby সাধারণত কাজ করে না** — active-active-এর পক্ষে এটাই সবচেয়ে শক্ত যুক্তি
- **Failback manual করুন।** স্বয়ংক্রিয় failback ওঠানামা ঘটায়।
- **আগে উপশম, পরে বোঝা।** Rollback, flag, failover, load shed।
- **Incident Commander-কে তদন্তকারী থেকে আলাদা করুন**
- **মালিক আর তারিখ সহ দোষারোপহীন postmortem** — দোষারোপ আপনার আগাম সতর্কতা ধ্বংস করে
- **গুরুত্বপূর্ণ পথ চিহ্নিত করুন আর রক্ষা করুন**; বাকি সব দুর্বল হতে দিন

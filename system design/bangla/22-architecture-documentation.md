## ২২.১ বেশিরভাগ architecture documentation কেন ব্যর্থ হয়

সবাই এটা দেখেছেন: একটা ৯০ পাতার Word নথি, প্রজেক্ট শুরুর আগে একবার লেখা, এমন একটা সিস্টেম বর্ণনা করছে যেটার আর অস্তিত্ব নেই, এমন একটা share drive-এ রাখা যেটা কেউ খুঁজে পায় না।

**কেন ব্যর্থ হলো:**

| ব্যর্থতা | কারণ |
|---------|-------|
| কেউ পড়ে না | খুব লম্বা, ভুল শ্রোতা, কোনো স্পষ্ট উদ্দেশ্য নেই |
| এটা ভুল | কখনো হালনাগাদ হয়নি; কোড এগিয়ে গেছে |
| কেউ খুঁজে পায় না | ভুল জায়গা — কোডের পাশে নয় |
| এটা *কী* বর্ণনা করে, *কেন* নয় | কোড তো কী সেটা দেখায়ই; শুধু মানুষই কেন জানে |
| এটা একবার লেখা হয়েছিল, সবচেয়ে খারাপ মুহূর্তে | কিছু শেখার আগেই |

**যে চারটা নিয়ম সব ঠিক করে:**

১. **Documentation কোডের সাথে থাকে** (repo-তে, version control-এ, PR-এ review হয়)
২. **আলাদা শ্রোতার জন্য আলাদা নথি** — একটা নথি সবাইকে সেবা দিতে পারে না
৩. ***কী* নয়, *কেন* লিপিবদ্ধ করুন** — কোড কী দেখায়; শুধু একজন মানুষই কেন লিপিবদ্ধ করতে পারে
৪. **ছোট, হালনাগাদ নথি বড়, বাসি নথিকে হারায়** — হালনাগাদ রাখতে না পারলে লিখবেনই না

> **Documentation-এর পরীক্ষা: শুধু repository ব্যবহার করে একজন দক্ষ নতুন ইঞ্জিনিয়ার কি এক সপ্তাহে উৎপাদনশীল হতে পারেন?** জিনিস কোথায় আর কেন বুঝতে তাঁর তিনটা কথোপকথন লাগলে, পাতার সংখ্যা যাই হোক, আপনার documentation ব্যর্থ।

## ২২.২ C4 Model ⭐ 🟢

Simon Brown-এর C4 architecture diagram-এর সবচেয়ে ভালো সাধারণ পদ্ধতি, কারণ এটা সবচেয়ে বড় সমস্যাটা সমাধান করে: **একটা diagram-এ abstraction-এর স্তর মেশানো**।

ক্লাসিক খারাপ diagram-এ একজন ব্যবহারকারী, একটা load balancer, একটা Java class, একটা AWS region, একটা database table আর একটা HTTP header সব একই ছবিতে। এটা পড়া যায় না কারণ এর কোনো সামঞ্জস্যপূর্ণ zoom-স্তর নেই।

**C4 আপনাকে চারটা zoom-স্তর দেয়, একটা মানচিত্র-অ্যাপের মতো।**

```
স্তর ১: CONTEXT      🌍  সিস্টেম আর তার চারপাশের পৃথিবী
স্তর ২: CONTAINER    🏢  এর ভেতরের deploy/চালানোর মতো জিনিসগুলো
স্তর ৩: COMPONENT    🔧  একটা container-এর ভেতরের প্রধান অংশ
স্তর ৪: CODE         📄  Class — সাধারণত generate করা, খুব কমই হাতে আঁকা
```

### স্তর ২ — Container ⭐ (আপনার আঁকা সবচেয়ে মূল্যবান diagram)

**শ্রোতা:** ডেভেলপার, আর্কিটেক্ট, operations।
**প্রশ্ন:** *Deploy করার একক গুলো কী, প্রতিটার টেকনোলজি কী, আর এরা কীভাবে যোগাযোগ করে?*

### স্তর ৪ — Code

Class diagram। **দরকার হলে কোড থেকে generate করুন; হাতে রক্ষণাবেক্ষণ করবেন না।** এগুলো কয়েক দিনেই বাসি হয় আর IDE ইতিমধ্যেই আপনাকে এটা দেখায়।

### পরিপূরক C4 diagram

| Diagram | কী দেখায় |
|---------|-------|
| **Deployment** | Container গুলো infrastructure-এ কীভাবে বসে (region, AZ, cluster, instance) |
| **Dynamic** | একটা নির্দিষ্ট পরিস্থিতিতে container/component কীভাবে সহযোগিতা করে (একটা sequence diagram-এর মতো, তবে C4-র স্তরে) |
| **System Landscape** | পুরো প্রতিষ্ঠানের সব সিস্টেম, আর তাদের সম্পর্ক |

> **Diagram repository-তে টেক্সট হিসেবে রাখুন** (Mermaid, PlantUML, Structurizr DSL, D2)। তাহলে এগুলো version-controlled, diff-যোগ্য, pull request-এ review-যোগ্য, আর এগুলো নীরবে এমন একটা slide deck-এ ভেসে যেতে পারে না যেটা কেউ সম্পাদনা করতে পারে না। এমন একটা PNG-তে আটকে থাকা diagram যেটা কেউ এমন একটা টুলে এঁকেছিল যার licence আপনার আর নেই — সেটা একটা মৃত diagram।

### State machine diagram ⭐

**কীসের জন্য সেরা:** জীবনচক্র আছে এমন যে কোনো কিছু। কোড লেখার **আগে** এটা আঁকুন (অধ্যায় ০১, State pattern)।

```

           pass        │   │    │ fail   │ (< সর্বোচ্চ চেষ্টা)

              ▼            ▼
        ┌─────────┐  ┌──────────────┐
        │ PASSED  │  │   REVIEW     │──approve──► PASSED
        └─────────┘  │  (সীমারেখায়)  │──reject───► FAILED
                     └──────────────┘
              ┌────────────────────────┐
              │  FAILED  (চূড়ান্ত)      │◄── সর্বোচ্চ চেষ্টা / মেয়াদ শেষ
              └────────────────────────┘
```

**এটা কেন এত গুরুত্বপূর্ণ:** এটা **অবৈধ transition গুলো দৃশ্যমান করে**। একটা PASSED session কি PROCESSING-এ ফিরতে পারে? একটা মেয়াদোত্তীর্ণ session কি approve করা যায়? এই প্রশ্নগুলোর business-উত্তর আছে যা ঠিক করতেই হবে — আর একটা state diagram bug-এর আগেই আলোচনাটা বাধ্য করে।

## ২২.৪ Architecture Decision Record (ADR) ⭐⭐ 🟢

**অস্তিত্বশীল একক সর্বোচ্চ-মূল্যের documentation চর্চা।**

**সমস্যা:** ১৮ মাস পর কেউ জিজ্ঞেস করেন *"আমরা Kafka-র বদলে RabbitMQ ব্যবহার করেছিলাম কেন?"*। যাঁরা সিদ্ধান্ত নিয়েছিলেন তাঁরা চলে গেছেন। কোড *কী* দেখায়, কখনো *কেন* নয়। তাই টিম হয় এমন একটা সিদ্ধান্ত নিয়ে বাঁচে যা তারা বোঝে না, নয়তো সেটা বদলায় — প্রায়ই মূল কারণটা কঠিনভাবে আবার আবিষ্কার করে ফিরে আসে।

**সমাধান:** repository-তে, প্রতিটা উল্লেখযোগ্য সিদ্ধান্তে একটা ছোট markdown ফাইল।

```markdown
# ADR-0014: Verification job বিলির জন্য RabbitMQ ব্যবহার

তারিখ: 2026-09-12
অবস্থা: Accepted
সিদ্ধান্তকারী: Delower Hosen (আর্কিটেক্ট), Platform টিম
প্রতিস্থাপন করে: —
প্রতিস্থাপিত হয়েছে: —

## প্রেক্ষাপট

Verification job গুলো API থেকে GPU worker-দের কাছে বিলি করতে হবে।

Constraint আর শক্তি:
- Peak volume ~১২০ job/মিনিট (২/সেকেন্ড), গড় ০.৬/সেকেন্ড। কম volume।
- Job-এ ৩-৬ সেকেন্ড লাগে; ব্যর্থতায় backoff সহ retry, তারপর manual পরিদর্শনের
  জন্য dead-letter করতে হবে।
- টিমের ৩ বছরের RabbitMQ operational অভিজ্ঞতা আছে; Kafka-র কোনো নেই।
- আমরা ৪ জন ইঞ্জিনিয়ার, কোনো platform বিশেষজ্ঞ নেই।
- ঐতিহাসিক job replay করার কোনো বর্তমান বা পরিকল্পিত চাহিদা নেই।
- প্রতি-message দৃশ্যমানতা (পরিদর্শন, retry, একটা poison message ফেলে দেওয়া)
  operational-ভাবে গুরুত্বপূর্ণ — আমাদের support টিম আরেকটা product-এ এটা ব্যবহার করে।

## বিবেচিত বিকল্প

### ১. RabbitMQ (quorum queue)
+ অন্তর্নির্মিত প্রতি-message ack/nack, TTL-ভিত্তিক retry queue আর DLQ (অধ্যায় ০৬)
+ টিম ইতিমধ্যেই এটা চালায়; runbook আর monitoring আছে
+ Managed বিকল্প উপলব্ধ (Amazon MQ / CloudAMQP)
− গ্রহণ করা message-এর কোনো replay নেই
− Throughput-এর ছাদ কম (২/সেকেন্ডে অপ্রাসঙ্গিক)

### ২. Apache Kafka
+ Replay, খুব উঁচু throughput, শক্তিশালী ordering-এর নিশ্চয়তা
+ ভবিষ্যতের একটা analytics event stream-ও সামলাত
− প্রতি-message retry/DLQ নেই — নিজেদের retry topic বানাতে হতো
− Kafka-র অভিজ্ঞতা নেই এমন একটা টিমের জন্য উল্লেখযোগ্য শেখার বক্ররেখা
− অতিরিক্ত: আমরা এর throughput ক্ষমতার ~০.০১% ব্যবহার করতাম

### ৩. AWS SQS
+ পুরোপুরি managed, প্রায়-শূন্য operation, আমাদের volume-এ সস্তা
+ নিজস্ব DLQ আর visibility timeout
− AWS-এ vendor lock-in
− RabbitMQ-র topic exchange-এর চেয়ে দুর্বল routing (আজ লাগছে না)

## সিদ্ধান্ত

আমরা একটা managed service হিসেবে deploy করা **quorum queue সহ RabbitMQ** ব্যবহার করব।

## ফলাফল

ইতিবাচক:
- TTL + dead-letter exchange দিয়ে retry-with-backoff আর DLQ সাথে সাথেই উপলব্ধ
- টিম প্রথম দিন থেকেই এটা চালাতে পারে; কোনো নতুন on-call জ্ঞান লাগে না
- Support-এর জন্য প্রতি-message operational দৃশ্যমানতা

নেতিবাচক:
- কোনো job replay নেই। পরে ঐতিহাসিক job আবার process করা লাগলে আমাদের
  broker থেকে নয়, `sessions` table থেকে সেগুলো আবার বানাতে হবে।
- পরে একটা analytics event stream বানালে একটা দ্বিতীয় broker লাগবে।
  (উপশম: ওটার জন্য আমরা Kafka ব্যবহার করব, আর task queue-র জন্য RabbitMQ রাখব।
   দুটো চালানো গ্রহণযোগ্য — এরা আলাদা উদ্দেশ্যে কাজ করে।)

নিরপেক্ষ:
- Message-এ একটা `schema_version` header থাকে, যাতে payload বিকশিত করা যায় (অধ্যায় ০৬)।

- টেকসই job volume সেকেন্ডে ৫,০০০ ছাড়ায়, অথবা

- আমরা একটা event backbone-এর জন্য Kafka নিই আর একত্রীকরণ সার্থক হয়ে ওঠে
```

| **আক্রমণাত্মকভাবে মুছুন** | একটা ভুল নথি একটা অনুপস্থিত নথির চেয়ে খারাপ — এটা সক্রিয়ভাবে বিভ্রান্ত করে |

> **যে নিয়মটা সবকিছু ঠিক করে: একটা নথি হালনাগাদ রাখার মতো না হলে, সেটা লেখারও মতো নয়।** আশিটা বিভ্রান্তিকর পাতার চেয়ে পাঁচটা সঠিক পাতা ভালো। সন্দেহ হলে কম লিখুন আর সেটা সত্য রাখুন।

## ২২.৮ আলাদা শ্রোতার কাছে architecture উপস্থাপন 🟢

একই সিস্টেমের আলাদা কাঠামো লাগে। এটা ভুল করাই আর্কিটেক্টদের ঘর হারানোর কারণ।

| শ্রোতা | তাঁরা যা নিয়ে ভাবেন | তাঁদের দেখান | তাঁদের দেখাবেন না |
|----------|----------------|-----------|------------------|
| **Executive** | খরচ, ঝুঁকি, সময়সীমা, business-এর ক্ষমতা | C4 Context, প্রতি-transaction খরচের সংখ্যা, ঝুঁকির টেবিল | Container diagram, টেকনোলজির নাম |
| **Product manager** | কী সম্ভব, কত খরচ, কখন | Context + একটা ক্ষমতার মানচিত্র, feature-এর ভাষায় trade-off | Container-স্তরের নিচে যা কিছু |
| **ডেভেলপার** | জিনিস কোথায়, কীভাবে নিরাপদে বদলাব | **Container + Component diagram, ADR, repo** | Executive-এর কাঠামো |
| **Operations / SRE** | কী fail করে, কীভাবে ঠিক করব, কী দেখব | Deployment diagram, runbook, dependency-র মানচিত্র, SLO | Domain model-এর বিবরণ |
| **Security / compliance** | Data কোথায় যায়, কে দেখতে পারে | Data flow + trust boundary, threat model, retention-এর টেবিল | Implementation-এর বিবরণ |
| **Auditor** | নিয়ন্ত্রণ আছে আর মানা হয় তার প্রমাণ | ADR, access রিভিউ, audit-log-এর নমুনা, retention policy | অনুমানভিত্তিক roadmap |

### আপনার architecture-এর elevator pitch

এটা ৬০ সেকেন্ড আর অনায়াস না হওয়া পর্যন্ত অনুশীলন করুন:

> *"এটা একটা queue-র পেছনে একটা Python API, আর GPU worker গুলো আসল liveness inference করে। Postgres হলো system of record; ভিডিও সোজা object storage-এ যায় আর compliance-এর জন্য ৯০ দিন পর মুছে যায়। এটা তিনটা availability zone জুড়ে Fargate-এ চলে। প্রধান ঝুঁকি হলো একটামাত্র face-analysis ভেন্ডরের উপর নির্ভরতা, যেটা আমরা একটা circuit breaker আর একটা manual-review fallback দিয়ে সামলাই। প্রতি verification-এ প্রায় ১.৪ সেন্ট খরচ হয়, আর দাম ১৫ সেন্ট।"*

ওই অনুচ্ছেদে আছে: topology, data-র মালিকানা, compliance-এর অবস্থান, deployment-এর মডেল, প্রধান ঝুঁকি আর তার উপশম, আর unit economics। **একজন আর্কিটেক্ট শুনতে এমনই।**

## ২২.৯ সাধারণ ভুল

১. **৯০ পাতার নথি যা কেউ পড়ে না** — একবার লেখা, এক মাসে বাসি
২. **কোড থেকে আলাদা documentation** — এটা ভেসে যাবেই, নিশ্চিত
৩. **একটা diagram-এ abstraction-এর স্তর মেশানো** — ক্লাসিক অপাঠ্য architecture-ছবি
৪. ***কেন*-এর বদলে *কী* নথিভুক্ত করা** — কোড তো কী সেটা দেখায়ই
৫. **কোনো ADR নেই** — সিদ্ধান্ত নিয়ে চিরকাল তর্ক হয়, তারপর উল্টে যায়, তারপর আবার উল্টে যায়
৬. **একটা accepted ADR সম্পাদনা করা** — ইতিহাসটাই মূল্য; বরং প্রতিস্থাপন করুন
৭. **লেবেলবিহীন তীর** — protocol বা payload ছাড়া একটা তীরের কোনো মানে নেই
৮. **উৎস ছাড়া ছবি হিসেবে diagram** — সম্পাদনা-অযোগ্য, diff-অযোগ্য, শেষে ব্যবহার-অযোগ্য
৯. **হাতে রক্ষণাবেক্ষণ করা class diagram** — কয়েক দিনেই বাসি; generate করুন
১০. **একটা নথিতে কোনো মালিক বা তারিখ নেই** — কেউ বিচার করতে পারে না এটা বিশ্বাস করা যায় কিনা
১১. **কখনো বাসি documentation না মোছা** — একটা ভুল নথি না থাকার চেয়ে খারাপ
১২. **সব শ্রোতার জন্য একটা নথি** — এটা কাউকেই সেবা দেয় না
১৩. **জীবনচক্র আছে এমন কিছুর জন্য কোনো state diagram নেই** — অবৈধ transition production-এর bug হয়ে যায়
১৪. নিয়ন্ত্রিত data সামলানো একটা সিস্টেমে **কোনো data-flow diagram নেই** — compliance রিভিউয়ের কোনো ভিত্তি নেই

- **প্রতিটা তীরে লেবেল দিন** — কী যায় আর কীভাবে
- **ADR সর্বোচ্চ-মূল্যের documentation চর্চা** — এগুলো *কেন* ধরে রাখে, যা আর কিছুই পারে না
- **আবার ভাবার trigger সহ immutable ADR** সিদ্ধান্তকে পেশাদার, ফেরানো-যোগ্য প্রতিশ্রুতিতে পরিণত করে
- **কোডের আগে state machine**; নিয়ন্ত্রিত যা কিছুর জন্য **data flow diagram**
- **যা পারেন generate করুন**: OpenAPI, ERD, lineage, class diagram
- **হালনাগাদ রাখার মতো না হলে লেখারও মতো নয়** — আশিটা মিথ্যা পাতার চেয়ে পাঁচটা সত্য পাতা ভালো
- **আলাদা শ্রোতার আলাদা নথি লাগে** — আর সাবলীলভাবে ভাষা বদলাতে পারা একজন আর্কিটেক্টের মূল দক্ষতা

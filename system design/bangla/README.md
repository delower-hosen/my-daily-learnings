# সিস্টেম আর্কিটেক্টের মানচিত্র

**যে ডেভেলপাররা System / Solution Architect হতে চান, তাঁদের জন্য একটি ব্যবহারিক বই।**

সহজ বাংলায় লেখা। প্রতিটা বিষয়ে *কীভাবে কাজ করে* বলার আগে বলা হয়েছে *এটা কোন সমস্যার সমাধান করে*।

> 🇬🇧 **English version:** [The System Architect's Map](../README.md)

---

## অনুবাদ নিয়ে দুটো কথা

এই বইটা **সহজ বাংলায়** লেখা, কিন্তু **technical শব্দগুলো ইংরেজিতেই রাখা হয়েছে**। কারণটা ইচ্ছাকৃত:

- বাংলাদেশ ও পশ্চিমবঙ্গের ডেভেলপাররা বাস্তব জীবনে এভাবেই কথা বলেন — ব্যাখ্যা বাংলায়, পরিভাষা ইংরেজিতে।
- `write-ahead log`-কে "লেখার-আগে লগ" লিখলে সেটা বোঝা সহজ হয় না, বরং কঠিন হয়। আর ইন্টারভিউ, ডকুমেন্টেশন বা Stack Overflow-তে আপনি ইংরেজি শব্দটাই খুঁজবেন।
- তাই: **ব্যাখ্যা, যুক্তি, উদাহরণ, গল্প — বাংলায়। Technical term, কোড, কমান্ড, error message — ইংরেজিতে।**

সংখ্যা বাংলা অঙ্কে লেখা হয়েছে (যেমন ৯৯.৯%), কিন্তু কোড আর কমান্ডের ভেতরে ইংরেজি অঙ্কই আছে।

---

## এই বইটা কেন

বেশিরভাগ শেখার উপকরণে দুটোর একটা সমস্যা থাকে:

১. **খুব ভাসাভাসা** — আপনি buzzword শিখলেন, কিন্তু সামনে একটা আসল সিস্টেম এলে আপনি জমে যান।
২. **খুব গভীর, খুব তাড়াতাড়ি** — আপনি তিন মাস Kafka-র ভেতরের কলকব্জা পড়লেন, অথচ এখনো একটা সিস্টেম ডায়াগ্রাম আঁকতে পারেন না।

এই বই মাঝের পথটা নিয়েছে, যেটাই **আর্কিটেক্টের পথ**:

> "কেউ আমার সামনে একটা নতুন সিস্টেম রাখলে আমার কখনোই মনে হওয়া উচিত নয় যে *'এই জিনিসটার নামই তো শুনিনি।'*
> আমার পরিভাষাটা চেনা উচিত, বোঝা উচিত এটা কোন সমস্যার সমাধান করে, জানা উচিত এটা কোথায় বসে —
> আর তারপর যখন পরিস্থিতি দাবি করবে, তখন production-এর খুঁটিনাটি শিখে নেব।"

তাই এই বই আপনাকে দেয় **এলাকার মানচিত্র**, প্রতিটা জায়গায় ঠিক ততটা গভীরতা সহ যাতে আপনি পারেন:

- মিটিংয়ে আত্মবিশ্বাসের সাথে ভাষাটা বলতে
- design review-তে সঠিক প্রশ্নগুলো করতে
- জানতে যে আপনি কোন trade-off নিচ্ছেন, আর কেন
- ঠিক করে বুঝতে *কোথায় আরও গভীরে খুঁড়তে হবে*, যখন প্রজেক্ট সেটা দাবি করে

## বইটা কীভাবে পড়বেন

প্রতিটা বিষয়ের সাথে একটা গভীরতার ব্যাজ দেওয়া আছে:

| ব্যাজ | মানে | আপনার যা পারা উচিত |
|-------|---------|-------------------------------|
| 🟢 | **গভীরভাবে জানুন** | ব্যবহার করা, debug করা, শেখানো, পছন্দটার পক্ষে যুক্তি দেওয়া |
| 🟡 | **ধারণা + কখন/কেন বুঝুন** | whiteboard-এ ব্যাখ্যা করা, trade-off জানা, সঠিকভাবে বেছে নেওয়া |
| ⚪ | **শুধু পরিচিতিই যথেষ্ট** | শব্দটা চেনা, কোন পরিবারের জিনিস জানা, কোথায় খুঁজতে হবে জানা |

প্রতিটা ⚪-কে 🟢 বানানোর চেষ্টা **করবেন না**। এভাবেই মানুষ ক্লান্ত হয়ে পড়ে আর কখনো আর্কিটেক্ট হয় না।

### পড়ার ক্রম

**আপনি যদি কর্মরত ডেভেলপার হন (সুপারিশকৃত):**
`০০ → ০১ → ০২ → ০৪ → ০৫ → ০৮ → ০৯ → ১১ → ২২` তারপর বাকিগুলো যে কোনো ক্রমে।

**আপনার যদি শীঘ্রই system design interview থাকে:**
`০৪ → ০৫ → ০৯ → ১০ → ১১ → ০৬ → ০৮ → ১৩ → ১৯ → ২৫`

**আপনি যদি সবে আর্কিটেক্ট হিসেবে পদোন্নতি পেয়ে থাকেন:**
`০০ → ২২ → ২৩ → ০৩ → ২৪ → ০২`

**আপনি যদি data platform বানান:**
`০৯ → ১০ → ১২ → ০৬ → ০৭ → ২৪`

## একটাই প্রশ্ন

এই প্রশ্নটা আপনি প্রতিটা অধ্যায়ে বারবার দেখবেন, কারণ পুরো কাজটাই এই:

> ### **এটা কোন সমস্যার সমাধান করে?**
>
> এটা নয়: *"এটা কীভাবে ব্যবহার করব?"*

একজন ডেভেলপার টুল জমান।
একজন আর্কিটেক্ট **সমস্যা** জমান — আর জানেন কোন সমস্যার উত্তর কোন টুল।

## আরও গভীরে

এখানকার প্রতিটা অধ্যায় একটা **মানচিত্র** — একটা ধারণা চেনার জন্য, সেটা কোন সমস্যার সমাধান করে জানার জন্য, আর কখন ব্যবহার করতে হবে বিচার করার জন্য যথেষ্ট।

কোনো বিষয়ে যখন আপনার **কলকব্জার স্তরের** গভীরতা দরকার — আসল algorithm, ধাপে ধাপে trace করা failure, চলমান implementation, আর production debugging — তখন দেখুন [**Deep Dive**](deep-dives/README.md) সিরিজ।
